Patch handoff and verification

Vega 20: review and patch priorities

Engineering handoff for Claude · 8 September 2026 · Four gfx906 dies, llama.cpp HIP backend

The useful next step

Preserve the reported MMVQ wins, recover their exact source, and profile the production executable before writing another kernel. Several proposed optimizations already exist in the stock build or its fork. The strongest remaining work is a careful MMVQ rebase, tuning existing attention kernels, determining whether whole-token graph capture is active, and making speculative draft limits stop actual work.

The supplied reports record substantial improvements: production Q8_0 prefill 848 → 1130 tok/s on four dies, and decode at 12 slots 122.3 → 198.6 tok/s. Those are valuable experimental observations. They do not establish that the tile table alone caused the prefill gain, or that the missing production patches are correct for every shape. Claude’s run-through, sections 10–11, production data.

Delivered with this review: two isolated optimizer patches fixing a Q4V crash, a generated-command error, and a throughput-constraint defect; six regression tests pass on the candidate. The original code, reports and settings remain unchanged. The GPU kernel proposals below are specifications requiring hardware validation, not claimed speedups.

Scope and evidence. Reviewed the local guide, optimizer, settings, benchmark tables, supplied Vega ISA and LLVM text; inspected pinned upstream b10288, b10837 and current source, the mxxm b10254 fork, and its ML-gfx906 recipe. No connection to the GPU host or GPU benchmark execution occurred. The two original MMVQ patch files, production binary, raw test logs and full build manifest are absent locally. Local measurements are therefore cited as reported, not independently reproduced.

Bugs and evidence errors in the project

P1 · Q4V selection crashes. optimize.py:112 looks up nonexistent n4_q8_0/q4_0 and n8_q8_0/q4_0 ladder keys before reaching the special Q4V table. Patch 0001 guards the missing ladder and preserves fallback modeling. It also moves the build warning out of the generated shell command: an inline # previously swallowed speculative flags appended afterward. Recorded 8-slot values, 152.8 at 2K and 107.4 at 32K, become reachable. Optimizer, patch 0001.

P1 · The solver can return a configuration below the requested speed floor. Topology and graph modifiers are indexed only by slot count and evaluated as TP4 inside the objective and constraint. The final result uses the real placement. A DP4-only, four-stream request for at least 20 tok/s per stream returns “Optimal” at 19.3: the constraint incorrectly credits the TP4 topology gain. Patch 0002 keys those modifiers by placement as well as slots. The same request becomes infeasible; a 19 tok/s floor remains feasible. This was reproduced using the real PuLP/CBC solver. Optimizer lines 534–595, patch 0002.

P2 · Production coefficients use the wrong build. _PB is loaded but unused. Production decode inherits the upstream-fastpath table: one die at eight slots uses 72.2 instead of the recorded production 69.1 tok/s. Correcting only that ratio reduces the published offline estimate from approximately 279.7 to 268.1 tok/s; the latter is still a model, not a four-instance measurement. Use exact production observations at matching conditions, and calibrate extrapolations from the same-session stock anchor. Build factors, lines 250–301, production table.

If cache time is C = slope × slots × depth/1024, the depth-independent speedup is (1000×slots/Tstock − C) / (1000×slots/Tprod − C). A raw throughput ratio is not this base-term ratio. At the recorded TP4 2K anchors, the base gains are approximately 1.087729, 1.632530 and 1.342907 for 8, 12 and 16 slots. These are derived calibration coefficients, not new measurements.

P2 · “Measured” currently includes unmeasured compositions. --measured-only filters before later modifiers change provenance. Production+MTP, deeper-context build extrapolations, a reused draft-depth factor, and transferred cap curves can survive with misleading labels. Moving the filter alone is insufficient. Track provenance separately for decode, prefill, memory, draft and power, then distinguish an exact joint observation from a composition of observed factors. Filter after complete composition. Solver lines 448–464 and 588–615.

P2 · Deep prefill gets the full short-context MMQ gain. The optimizer multiplies all prefill throughput by about 1.33, including attention cost. The 691 and 492 tok/s production predictions at 128K and 256K are not measured production cells. A defensible model accelerates only the affected component: time_new = time_matmul/gain + time_attention + time_other. Existing fitted components may themselves need refitting; use direct 32K/128K/256K measurements to settle this. Build and composition code, saved results, context report.

P2 · The cap curve mixes request and decode throughput. The 16-client cap study includes prompt time. The optimizer applies that ratio to decode and separately penalizes prefill, so its phase model can double-count the effect and transfer it to unmeasured placements. Preserve the cap curve as request-level evidence for its exact workload until separate phase timings exist. Also, two nodes at the documented 125 W cap provide a reported basis of 150.6 tok/s (2 × 75.3), not the 165 tok/s HA figure that assumes 155 W. Cap model, power study, fleet recommendation.

These modeling findings remain open; the two delivered patches deliberately address the reproduced execution and constraint defects. They do not certify the other predictions.

What Vega 7nm actually offers

The supplied AMD ISA establishes wave64, packed 16-bit operations, INT8/INT4 dot instructions, FP16-pair dots with an FP32 accumulator, and 64 KiB LDS per CU. gfx906 lacks the MFMA path used by later CDNA devices. The guide’s theoretical peak arithmetic at 1.730 GHz is consistent: approximately 14.17 TFLOP/s FP32, 28.34 TFLOP/s packed FP16, 56.69 TOPS INT8 and 113.38 TOPS INT4, counting multiply and add separately. Those are ceilings under issue-rate assumptions, not measured sustained rates. INT4 dot requires INT4 operands on both sides; four-bit weights with eight-bit activations do not directly qualify. AMD Vega 7nm ISA, 27 January 2020, §§2, 6.7, 12.10, supplied extraction.

The physical VGPR pool is 64 KiB per SIMD, equivalent to 256 wave-wide vector registers. Four-register allocation granularity makes 64 registers/thread compatible with four waves/SIMD, 65 round to 68 and permit three, and 113 round to 116 and permit two, before other limits. This explains a knee in the reported MMVQ experiments. It does not impose a universal 64-register optimum on attention or MMQ. LLVM resource calculation.

DPP can reduce cross-lane instruction overhead, but ds_bpermute uses LDS routing without allocating or accessing LDS memory. DPP patterns and active-lane semantics must fit the reduction. The ISA specifies two wait states for relevant VALU-to-DPP VGPR hazards and five for relevant EXEC hazards. A wave64 result also needs cross-row combination and, where required, broadcast. v_readlane transfers one lane to an SGPR; it is not a general per-lane gather. SDWA byte/halfword selectors do not directly extract arbitrary four-bit nibbles or fragmented six-bit scales. Supplied ISA §§4, 12.13, 13.3.7, 13.3.9, AMD cross-lane explanation, 2016.

An FP32 accumulator avoids repeated FP16 accumulator rounding; it does not guarantee equivalence to another evaluation order. LLVM’s gfx906 lowering explicitly considers FP16 subnormal behavior when contracting mixed operations into dot2. Preserve denormal, contraction and accuracy settings in every comparison. Throughput alone neither proves emitted opcodes nor proves a specific stall cause; 30% VALU busy does not assign every remaining cycle to loads. LLVM lowering, local utilization interpretation.

Patch queue for llama.cpp

1. Recover and rebase the measured MMVQ changes

Priority: highest; evidence: reported gains, incomplete source. Retrieve the two original patches and exact production commit, compiler commands, package versions, binary/model hashes and test logs from the benchmark directory before attempting a faithful transplant. The local patch README explicitly says those files still reside on the GPU host. Missing-source inventory.

For the rebase, keep dense quantized gfx906 eligibility separate from the shared global MMVQ limit. Both stock b10288 and current upstream assert that MMVQ and MMVF maximum batch sizes agree; changing one constant also touches dispatch outside the intended Q8 path. The existing GCN launch table is shared with CDNA. Introduce an exact gfx906 host/device selection and preserve float-vector, MoE/ID and other-architecture behavior. Port table selection and eligibility together. Current shared-width assertion, MMVQ tables and dispatch.

Acceptance: compile relevant HIP targets; verify batch sizes 1–17, 24 and 32, supported tails/strides, non-Q8 fallback and MoE IDs; compare backend errors and long-running model output; test graph replay and shape transitions. Benchmark one die and TP4 at short and deep context, with disassembly/resource metadata for every launch-table candidate. Recover the reported 1186-case inventory rather than assuming its count covers these boundaries.

Treat the MMQ transplant as a separate patch. The fork includes a gfx906 table plus host/device dispatch and a J>64 gate excluding MoE and grids with fewer tiles than CUs. Copying the table without those guards changes which workloads receive large tiles. Test Q8_0 and K-quants separately at decode widths 16/24/32, prefill 512/2048, and short tensor shards; the recipe's K-quant patch adds specific cases rather than a universal layout. Fork table, eligibility gate, K-quant patch.

2. Instrument graph and collective eligibility before replacing communication

Priority: highest for single-stream latency; gain unknown. Current upstream executes backend subgraphs and then allreduces outside those subgraph captures. The mxxm fork already offers whole-token graphs and custom TP allreduce. Its custom path is opt-in through GGML_ENABLE_CUSTOM_AR; token capture requires the relevant collective preparation to succeed. Add one-time, structured diagnostics for selected collective, message size/dtype, custom-path refusal reason, capture eligibility, and graph replay versus recapture. Upstream meta dispatch, fork collective initialization, fork capture eligibility.

Then compare eligible existing implementations in a bounded benchmark. Keep RCCL as the operational baseline. The measured losing GGML_CUDA_ALLREDUCE=internal path is not evidence about every custom collective, and the fork’s feature claims are not measurements on this production executable. AMD documents RCCL as graph-safe; end-to-end capture still depends on the caller and exact runtime. AMD graph-safe library matrix.

If a custom collective is still justified, first specify allocation coherency, peer access, integer system-scope release/acquire flags, generation counters, buffer reuse, graph replay ordering and forward progress. Plain stores plus a flag are not a complete protocol. Coarse-grained memory does not provide the same in-kernel system-scope guarantees as fine-grained memory; fine-grained allocations can have a cache-policy cost. Test delayed ranks, repeated replays, concurrent requests and dtype/size fallback before measuring latency. HIP coherence, AMD atomic scopes.

The reported 13 ms is a residual from a weight-streaming model, not measured RCCL time. Link bandwidth and one-hop latency do not prove a sub-10 µs allreduce or a +19–23% model gain. Use the actual critical-path reduction, including launch and consumer time, to calculate an Amdahl bound. Original timing decomposition.

3. Tune the attention path already using packed arithmetic

Priority: high for deep contexts; gain unknown. Keep QK/PV precision unchanged in the first experiment. Log head dimensions, query count, GQA ratio, mask/stride case, chosen kernel, tile dimensions, split count, scratch bytes, VGPRs and LDS. Sweep a small gfx906-specific neighborhood around the current launch decisions and sequence-splitting heuristic. Include the combine-kernel and scratch-traffic costs; increasing parallel blocks is not automatically faster. Existing FA tile path, FA vector path.

Acceptance: head size 256, 1/4/8/16 active sequences, short prefill and 32K/128K/256K depths, supported masks and KV formats. Use correctness comparisons against the existing backend and a higher-precision reference where practical. Arithmetic changes need cancellation, tiny-probability, large-value and long-context tests in addition to perplexity. Do not infer that lower reported utilization means an absent instruction.

The existing split heuristic already uses actual device CU count and occupancy. The refinement is to price launch/combine overhead and workload shape more accurately, not to replace an assumed NVIDIA-only SM count. Current occupancy-based selector.

4. Skip activation sums only with a valid consumer/cache contract

Priority: medium; bounded producer optimization. Add a compile-time need_sum specialization to the Q8_1 activation producer for proven Q8_0-only consumers. Initially retain the Q8_1 record stride and alignment, preserving scale/quant rounding. The expected saving is producer-side sum reduction/work; the existing dot consumer already ignores that field. Inspect generated code to establish whether any consumer load changes at all. Q8_1 quantizer, Q8 dot consumer.

The fork reuses quantized activations across operations. A no-sum buffer must have a distinct cache-validity variant or an established all-consumer proof, or an affine quantized consumer can reuse invalid sums. Test mixed Q8_0/affine consumers sharing activations, graph replay and buffer reuse, then measure quantization plus consumer time together. Avoid a global switch to the differently sized Q8_0 activation representation. Fork quantization and reuse implementation.

5. Make adaptive drafting stop the MTP loop

Priority: medium; concrete server/backend integration. The current generic speculative wrapper can truncate a result to the per-sequence dp.n_max after drafting has occurred. A server-only cap can therefore retain the full drafting cost. Enforce the effective limit inside the MTP loop and stop queuing work for finished sequences. Zero-budget sequences must skip drafting; in the wrapper, nonpositive n_max is not a truncation request. Current speculative implementation.

Use actual verification-batch composition, backend eligibility and observed acceptance to choose limits; active_slots × (draft+1) is only an approximate bound for uniform drafts. Validate zero/one/multiple-token budgets, EOS, mixed per-slot limits, acceptance and rejection rollback, and graph-size changes. Measure emitted MTP decode calls as well as output length. Do not assume the production kernel automatically makes drafting at eight streams profitable.

6. Tune remaining recurrent and reduction work only after tracing

Priority: conditional. Focus on launch-table choices for the existing fused recurrence and genuinely unfused surrounding gates/norms, preserving state ownership and speculative rollback. The model’s megabytes of state per layer cannot fit in one 64 KiB LDS allocation; existing kernels shard the state. Do not budget the entire fitted per-layer residual as removable launch time. Stock state-sharded recurrence.

For DPP, change one hot reduction with known subgroup width and active-mask semantics, using compiler-visible intrinsics where possible. Inspect hazard spacing and numerical changes, test result-lane/broadcast requirements, then benchmark the enclosing kernel. For K-quant unpacking, target one emitted extract/consumer sequence that SDWA or packed integer math can actually replace. Treat scheduling barriers as compiler controls, not hardware synchronization or an assured performance gain.

Dependency-stack priorities

LLVM/HIP: pin the compiler and retain the current working stack while testing candidates in a separate prefix/build. Compile for gfx906 and inspect target IDs and code objects directly; do not infer target features or ECC mode from achieved bandwidth. A code-object-version change is a compatibility experiment before it is a performance experiment. Compare the scheduler already used by the recipe with controlled alternatives on a fixed source revision, recording ISA, registers, spills and timings. LLVM target and code-object documentation, ML-gfx906 recipe.

rocBLAS/hipBLAS: prioritize packaging and load correctness for the fallback paths, not another blanket force-BLAS prefill trial that the project already measured. Current TheRock source registers gfx906 but excludes hipBLASLt, hipSPARSELt, Composable Kernel, rocWMMA, hipTensor and rocprofiler-compute for it; rocBLAS is not in that exclusion list. Older claims that TheRock excludes rocBLAS cannot be carried forward unchanged. Validate the actual installed libraries and target code objects; target registration does not certify every library build. Pinned TheRock target policy, 8 September 2026.

ROCm distribution: official support and a functioning custom TheRock build are different questions. AMD’s current Linux matrix marks MI50, Radeon VII and Radeon PRO VII gfx906 products unsupported; it does not erase Claude’s observed working build. Preserve exact working component versions and runtime smoke tests instead of assuming the newest prebuilt stack supports this hardware. AMD Linux requirements.

Profiler: the current kernel-only command cannot count HIP graph API launches. Collect HIP APIs, kernels and markers; add RCCL API tracing if the installed version supports it. Enumerate available counters before relying on hard-coded names. Separate low-overhead timeline collection from counter passes, which can perturb concurrency. Newer profiler documentation describes JSON/rocpd graph attribution that direct CSV omits; check the installed version before using it. AMD rocprofv3 guide.

# Proposed trace command; run only under the project's existing power/watchdog setup.

Add ROCTX token/ubatch ranges where available, correlate graph launches and collectives, and compute the union of intervals per device. Do not sum concurrent kernel durations over four dies and call that token wall time. Exclude model loading, warmup and graph construction; compare with an unprofiled timing run. Keep counters, clocks, package versions and shape metadata with the trace.

Acceptance sequence and handoff

  1. Preserve the exact production source and binary manifest; apply the optimizer fixes in Claude’s working copy and correct provenance before republishing recommendations.
  2. Reproduce the reported production table under the same power, context and workload conditions; add confidence intervals from repeated paired runs. Differences within the project’s reported 2% band do not justify a performance claim.
  3. Trace single-stream TP4 and one die. Inspect existing graph/custom-allreduce eligibility. Select work by measured critical-path time.
  4. Rebase the MMVQ path with exact gfx906 guards; validate 9–16 boundaries and fallback behavior. Run the open production depth, 24/32-slot and MTP cells.
  5. Tune attention without changing precision. Pursue cache-safe sum elimination, MTP loop limits and hot reductions as separate changes, each with its own correctness and performance gate.

The operational wins and measured losers in Claude’s reports remain useful. This review does not recommend rerunning the nineteen exhausted environment knobs, disabling graphs, reverting to the losing internal allreduce, or replacing the established power policy. The one unexplained clamp episode in the source report also means the supply explanation should remain the best-supported diagnosis rather than a proven explanation of every event. Run-through.
