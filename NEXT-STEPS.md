## Part 2 — The software stack, ranked

Effort: **flag** (no rebuild), **patch** (a few lines), **kernel** (one kernel), **subsystem** (several files or a new component). Gains are on the production build unless noted; "measured" means the number exists in `reports/`, otherwise it is the bound the data implies.

### S1. Make the two gfx906 kernel wins durable — upstream them
Effort: patch → subsystem. Gain: none beyond the measured +33% prefill / +8–62% decode, but it removes the fork dependency and survives the next rebase. **Ablation (2026-09-08, TODO 12, `tile_table_ablation`):** the MMQ config table with its dispatch guard is 89% of the fork's Q8_0 prefill gain on its own (+30% four dies, +37% one die) and all of its 16–32-slot decode gain (+16–21%); the K-quant gains (+26% Q6_K, +7% Q4_K_M) are the fork's K-quant kernels, a separate patch. That is the upstream PR's scope: one header, one guard, the K-quant kernels after.

The fork's tile table is a per-target table for the integer matrix kernel; upstream ggml picks its MMQ tile shapes (`mmq_x`, `nwarps`, the `MMQ_ITER_K` loop) from RDNA/CDNA/NVIDIA-shaped tables and falls to a generic one on GCN. The fix is a `GCN` (or `__gfx906__`) case in the tile selector carrying the fork's shapes, chosen for 64 KB LDS × 32 banks and wave64 at four resident waves. The MMVQ changes are a `MMVQ_PARAMETERS_GCN` table (rows 4 / warps 1 to 8 columns, rows 2 / warps 1 above), the 16-column instantiations, and the Q8_0 fast path guarded by the same macro. `test-backend-ops` already passes 1186/1186 on all of it; perplexity is identical to four digits. Until it is upstream, keep `patches/` current with every rebase (M5).

Review 2026-09-08 guidance for the rebase: keep the gfx906 eligibility separate from the shared `MMVQ_MAX_BATCH_SIZE` — upstream asserts `MMVQ_MAX_BATCH_SIZE == MMVF_MAX_BATCH_SIZE`, and the GCN launch table is shared with CDNA, so the width change needs an exact gfx906 host/device selection that leaves the float-vector, MoE/ID and other-architecture paths alone; port the table and the eligibility together. ### S2 (analysis). Cross-die synchronisation: replace the 128 RCCL kernels per token
Effort: kernel → subsystem. Measured (M1): 128 allreduces per token (two per block), 27 µs each on the GPU, 3.4 ms of the 21.5 ms token (16%); the graph launches around them cost at most the 1.1 ms the die is idle (5%).

M1 settled the shape of the work. The meta backend (`ggml/src/ggml-backend-meta.cpp`) cuts the model graph at every partial-sum node and runs each segment as its own `graph_compute` on each die with an RCCL group call between segments, so a token is 129 HIP graph launches per die with the allreduces in between — split around the allreduces by construction, not by accident. But the host stays ahead of the GPU: idle inside the token is 1.1 ms, 0.85 ms of it ~150 sub-10 µs dispatch gaps inside the graphs and the rest at the 16 host stream synchronisations per token. Capturing RCCL inside the graph (RCCL 2.30.4 supports capture) therefore buys at most 5% and is demoted; the 16 host syncs are worth 1–2% and are not worth a change on their own.

The 3.4 ms is kernel time: `ncclDevKernel_Generic_4` at 27 µs for a message of one hidden vector in fp32, against a 507 ns one-hop read latency and 33 GB/s per link. The fix is a latency-optimised 4-die allreduce for ≤ 64 KB messages: each die writes its slice into the three peers' fine-grained buffers over XGMI and raises a flag, peers spin on flags and sum locally — one wave per die, direct peer stores plus flags, no copy engines (they are the wrong tool at kilobytes; `GGML_CUDA_ALLREDUCE=internal` is the idea without the latency work and measured −23%). At 5–8 µs per allreduce that returns 2.5–2.8 ms, **+13–15% single-stream**, and a plain kernel is graph-capturable for free. Fusing the reduce into its consumer — the residual add and norm read the four partial sums directly, three of them over XGMI — removes one more kernel per allreduce and belongs with S3.

### S3 — measured 2026-09-08: fusion is worth ~3%, not 15–20%; the lever is overlap
Three fusions were built and measured (`reports/2026-09-08-next-steps-measurements.md`, "Kernel fusions"; `patches/0001–0003`): norm emits q8 (exact, 0%), residual add inside the norm (exact, +1.6%), delta-net producers folded into the GDN kernel (+1.8% but changes numerics; under investigation). Kernels per token fell 1866 → 1466 and the fused norm+q8 kernel takes exactly what norm + quantize took: **the small kernels are latency-bound, not launch-bound**, so fusing dependent phases keeps their latency. Running independent kernels concurrently was the remaining idea — the fork's multi-stream graph optimisation, gated to single-device processes until commit a1462e0 (`GGML_CUDA_GRAPH_OPT=2`) — and it measured **0** on both placements: the small kernels sit on each block's single dependency chain. Their 5.8 ms is intrinsic latency; only a persistent per-block kernel (a different execution model) would recover it. The original analysis follows.

### S3 (analysis). Fuse the small kernels
Effort: kernel. Measured (M1): 1,305 kernels per token per die that are neither matrix-vector nor RCCL, 5.8 ms of the 21.5 ms token on tp4 (27%); 1,225 kernels and 6.4 ms of the 50.9 ms token on one die (12.5%). They run back to back inside the HIP graphs (the die is 95% busy), so this is kernel execution at the ~4 µs floor of a GCN dispatch, not launch overhead; only fewer kernels help.

Per token per die on tp4: 257 `quantize_q8_1` (1.0 ms) ahead of the matrix-vector kernels; 209 `rms_norm` and 96 `l2_norm` (1.5 ms); 176 residual adds (0.7 ms); 64 `cpy` and 32 `rope` (0.4 ms); the 48 linear-attention blocks' chain — `ssm_conv`, `gated_delta_net`, sigmoid, silu, softplus, concat, two `get_rows`, `set_rows`, about nine kernels per block — 430 kernels, 1.7 ms; 32 flash-attention kernels (0.4 ms). In order of value: (1) fuse the activation quantisation into the norm that precedes it — norm + quantize as one kernel, 257 launches gone, ~1 ms; (2) fuse the residual add into the following norm and, on the split, into the allreduce consumer (S2); (3) one fused kernel per linear-attention block, state in registers and LDS (standard for gated delta nets; the per-token work is tiny and the cost is entirely dependent tiny kernels), ~430 launches, ~1.5 ms; (4) rope and the KV `set_rows` into the attention path. Realistic: 3–4 ms of the 5.8, **+15–20% single-stream on tp4, +8% on one die**, and it carries into batched decode unchanged because these kernels do not grow with the batch. Same rule as the MMVQ work: fewer instructions, no barriers, about 64 VGPRs.

### S4. Flash attention at head size 256 for GCN
Effort: kernel. Bound: prefill at 256K is 72% attention at 8.3 TFLOP/s per die (30% of packed-fp16 peak); decode at depth reads the cache at 369 GB/s per die (41% of HBM). Halving attention time takes a 256K prompt from 12 minutes to ~7.5 and adds 20–40% to decode at 128K–256K.

**Correction (review 2026-09-08, verified in the source):** stock b10288 already defines `V_DOT2_F32_F16_AVAILABLE` for `__gfx906__` (`common.cuh:753`) and the vector and tile attention kernels use it, so "add packed fp16 dots" is not the work; and the split-K heuristic already uses the device CU count and occupancy (`fattn-common.cuh`), not an NVIDIA SM count. What remains, in order of certainty: first, a per-target tile table for the FA tile kernel, the same fix that gave MMQ +33%, with tile shapes chosen for 64 KB LDS and wave64; second, pricing the launch/combine and scratch-traffic cost of the sequence split more accurately on 64 CUs at 32K–256K (more parallel blocks are not automatically faster); third, only if the emitted ISA shows unpacked arithmetic, `V_PK_FMA_F16` for the PV products where half2 accumulation is acceptable. Keep QK/PV precision unchanged in the first experiment; log head size, query count, GQA ratio, mask case, chosen kernel, tile shape, split count, scratch bytes, VGPRs and LDS; test cancellation, tiny-probability, large-value and long-context cases besides perplexity. Instrument with the same counters that worked on MMVQ (`SQ_INSTS_VALU`, `SQ_BUSY_CYCLES`, `SQ_WAIT_INST_ANY`, `TCP_TOTAL_CACHE_ACCESSES`) before changing anything.

**Counters and disassembly (2026-09-08, `reports/2026-09-08-fa-counters.md`, BENCHMARKS-TODO 9):** only `SQ_INSTS_VALU` of those four exists for gfx906 on ROCm 7.14 (the gfx906 set is `GRBM_GUI_ACTIVE`, `SQ_WAVES`, `SQ_ACTIVE_INST_VALU`, `SQ_INSTS_VMEM_RD/LDS`, `SQ_WAIT_INST_LDS`, `TCC_HIT/MISS`; a second pass with those is queued). Attention is 17% of a 32K prompt's kernel time on the split and 19% of a 128K decode token. The prefill kernel `flash_attn_tile<256,256,16,2>` runs **two waves per SIMD** (89 VGPRs and 26.5 KB of LDS both cap it there) and issues VALU on 45% of the cycles; its KV loop is 1,842 instructions with 193 `s_waitcnt` and 208 LDS reads per 1,040 `v_dot2`/`v_pk` instructions — latency-bound at low occupancy, so the tile table's first target is a shape that fits three waves per SIMD (≤ 84 VGPRs, ≤ 21.8 KB LDS). The decode kernel `<256,256,1,2>` is a KV-streaming kernel (17% VALU, ≥ 441 GB/s) that **reads the same KV three times per token per die**: the model's GQA ratio is 6 and `fattn.cu` packs heads by divisibility (8, 4, 2), so `ncols2 = 2` and three head-pair blocks stream each slice. A six-head packing (`ncols2 = 8` with two idle lanes, or a 3-head variant; the head-256 instantiations for one column exist at `ncols2` 2/4/8) reads the cache once: floor 150 µs against 304 per layer, up to 9% of the 128K token, more at 256K. The corrected counters (queue 23, key `fa_counters_head256.pass2_gfx906_counters`) confirm the prefill reading: VALU busy 46–47%, 24 LDS instructions per global load, LDS wait 7.5 SE-cycles per GUI cycle, no bank conflicts, L2 hit 94–95%. Order of work: (1) the six-head decode packing (a dispatch and template change; its counters at depth need a `-ntg 128` pass), (2) the three-wave prefill tile (LDS-bound (working hypothesis from 2 waves/SIMD, 46–47% VALU busy and the instruction ratio; not yet separated from bank conflicts, dependency stalls or occupancy — S4 experiment): fewer LDS instructions per dot as much as more waves).

### S5. The server: draft length and mixed traffic
Effort: patch → subsystem. Measured bounds: adaptive drafting keeps the whole MTP curve above baseline at every concurrency (today 8 slots with any draft loses 20–27%); mixed traffic today holds short requests at 0.9 tok/s for the duration of a long prefill.

- **Adaptive draft length.** Choose the draft per step so that active slots × (draft + 1) stays at or below the matrix-vector kernel's width: 8 on stock, **16 on the production build (measured, M3)**: draft 3 at 1–4 active slots, draft 1 at 8 (worth it only at depth), none above. Implementation note from the 2026-09-08 review: the generic speculative wrapper (`common/speculative.cpp`) can truncate a draft to the per-sequence `n_max` *after* the drafting has run, so a server-side cap alone keeps the drafting cost; enforce the limit inside the MTP loop, skip drafting for zero-budget sequences (a non-positive `n_max` is not a truncation request), and measure emitted MTP decode calls, not only output length. The bound is approximate for non-uniform drafts; choose from the actual verification-batch composition and observed acceptance.
- **Mixed traffic.** `-b` is not the lever (measured); M6 finds what is. The likely candidates are how a hybrid-attention model's batch is split into micro-batches (recurrent-state models split by sequence, so a decode step and a prompt chunk may run as separate micro-batches each paying the per-layer overhead) and the fixed cost of the prompt chunk regardless of size. The fix is a decode-priority scheduler: when any slot is generating, cap the prompt tokens per step so a decode step lands at least every ~100 ms, and let the long prompt pay the difference. Until then the operational answer is routing by prompt length to two instances (`settings/launch.sh pairs`), which is measured.

### S6. Squeeze the matrix-vector kernel further
Effort: kernel. Bound: a few percent each; the kernel is now bound by instructions per dot product, so every instruction removed shows.

- **Batch-1 bandwidth — measured 2026-09-08 (`mmvq_batch1_variants`):** the whole-block load at one column is +2.8% on the split and +7.1% on one die and is now the default (commit d49570b); rows 2/4 per block help only one die; four warps lose. The remaining gap to HBM (~73% → 85%) is the next item below.
- **Batch-1 bandwidth (analysis, M1).** The single-column kernel streams at 604–611 GB/s on the split and on one die alike, 68% of the 890 GB/s the HBM delivers: 11.2 ms of the 21.5 ms token on tp4, 44.7 of 50.9 on one die. A batch-1-only instantiation is legitimate (the template is per column count) and the whole-32-weight-block load per thread was +5% at batch 1 before it lost at batch 8; 68 → 85% of HBM is worth 2–3 ms on tp4 (+10%) and 7–8 ms on one die (+15%). Third in the single-stream order after S3 and S2.
- Activation sums: **corrected 2026-09-08** — the Q8_0 × Q8_1 dot already reads only the scale (`__low2half(bq8_1->ds)`, `vecdotq.cuh`), so no consumer load or multiply goes away; the only saving is the producer's sum reduction in `quantize_q8_1` (and its fused copy in the norm), a compile-time `need_sum` specialisation for proven Q8_0-only consumers. ### S7. Multi-node tensor parallelism on ROCm — FUTURE STATE, out of scope for the current campaign

**Status (lead, 2026-09-21): not in scope for the llama.cpp patchset optimisation work. On the
future-state engineering task list.** Recorded here while the findings are fresh so it does not have to
be re-derived. The fleet is a multi-node cluster on Mellanox ConnectX InfiniBand; the cards go into PCIe
bays 5/6/7 after the patchset work lands, for large-model multi-node testing.

**What exists today, established by inspection of v0.4.1 on 2026-09-21:**
- Tensor-parallel splitting (`-sm tensor`) builds its communicator from `cudaGetDeviceCount()` inside a
  **single process**. There is no `ncclGetUniqueId` broadcast, no `ncclCommInitRank` per rank, no MPI and
  no rank/world concept anywhere in the CUDA/HIP backend. Remote GPUs cannot join that group.
- RCCL is supported by the build (`GGML_HIP_RCCL=ON`, required by R3.11) and RCCL itself does IB with
  GPUDirect RDMA — but llama.cpp never asks it to span nodes. It drives the local dies.
- The only multi-machine path in-tree is the **RPC backend** (`ggml/src/ggml-rpc`), which is TCP sockets
  (`send_msg`/`recv_msg` over `AF_INET`). No `ibv_*`, no RDMA verbs, no GPUDirect. Over IPoIB it would
  function and gain nothing from PeerDirect; tensors are serialised through host memory.
- The fork's custom AllReduce (`tp-allreduce.cu`) is explicitly an intra-node PCIe/XGMI design
  (release/acquire ordering chosen because PCIe has no hardware cache coherence). It is not a candidate
  for cross-node work and is not affected by this item.

**So the work is one of two designs, and the choice should be made deliberately:**

1. **Cross-process RCCL communicator in ggml.** Add a rank/world concept to the CUDA/HIP backend: rank 0
   creates a unique id, broadcasts it out of band, every rank calls `ncclCommInitRank`. The existing
   `comm_init_nccl` / `try_allreduce_nccl` dispatch already assumes a communicator vector, so the
   collective call sites may need less change than the bootstrap does. Hardest parts are process
   launch/discovery, buffer placement across nodes, and the scheduler's assumption that every backend is
   locally addressable.
2. **RDMA transport for the RPC backend.** Keeps llama.cpp's existing multi-machine structure and swaps
   sockets for verbs. Lower architectural risk, but the RPC backend serialises whole tensors per call, so
   it needs zero-copy GPU-registered buffers to be worth the cards — i.e. most of the win depends on the
   same peer-memory plumbing as option 1.

**Hard dependency for either:** GPUDirect RDMA on gfx906 requires the `amdgpu` peer-memory kernel module
(the `ib_peer_mem` / `peermem` interface). That must be verified on the barfix kernel before either design
is committed to — it is a kernel-side prerequisite, not an application concern, and this project already
maintains a custom kernel (see [[macpro-gpu-bar-resize-work]] territory in the fleet notes).

**Recommended sequencing:** scope this while the ConnectX cards are still out of the chassis. The worst
outcome is discovering the gap with hardware already racked. An upstream check is also owed first —
whether ggml has since gained any multi-node collective work — because authoring it ourselves is only the
answer if nobody upstream is already doing it.

### S9. Power governor and fleet scheduling
Effort: subsystem (a small daemon and a proxy rule). Measured basis: the SMC clamps the hive about 20 s after the DC total passes 1228 W; the production cap on hyperconverged nodes is 125 W because the host is uncapped there.

- **Governor:** read the SMC's DC total each second; when it passes ~1150 W, lower the four caps (`power1_cap`) in lockstep and restore them as the total falls. This restores the 140–200 W range on a node whose host may run all-core. **Measured (M7, 2026-09-08):** with the dies at 200 W caps and a 16-client server, a 56-thread host load reaches DC 1133 W at a 150 W host cap, 1172 W at 175 W and 1206 W at 200 W (~1.5 W of DC per watt of host cap), so 175 W is the last host cap inside the envelope at 200 W die caps; a 1150 W trigger with a 50 W host-cap cut (about −70 W DC) leaves three 5-s samples before the SMC's ~20 s clamp. The host load also costs the server 12% at the 150 W cap (82.3 → 72.1 tok/s): on shared nodes the serving threads want their own cores (`--threads` and a cpuset) before the governor matters.
- **Fleet:** route new streams to whichever node has floor capacity (16 slots at 85 W per die, 60 tok/s for 575 W DC) before raising any node's cap; raise caps in lockstep to 125 W; never above on shared nodes. `settings/powercap.sh` does the cap; the routing rule belongs in the proxy.
