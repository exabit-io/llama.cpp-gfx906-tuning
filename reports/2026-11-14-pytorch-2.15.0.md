# 2026-11-14: PyTorch 2.15.0 for gfx906 on ROCm 10.0 - package, typing_extensions backport, rolling apt channel

**What happened.** `python3-torch-gfx906` went from 2.14.1 to upstream PyTorch **v2.15.0** (`31a77fc`, released 2026-10-28;
torchvision 0.30.0, torchaudio 2.11.0), built against the installed ROCm 10.0.0-gfx906+20261018172427, and its apt
distribution moved from one release per version to the rolling channel `python3-torch-gfx906` on
`exabit-io/resize-amdgpu-bars`, like `mx-llama-cpp-gfx906` earlier the same day. Upstream dropped the gfx906 kernels from
its own ROCm wheels in 2.15 ("build from source with those targets in `PYTORCH_ROCM_ARCH`"), which is what this package is.

All runs: macpro2019-01, 4x gfx906, GPUs at 125 W, system interpreter (`/usr/bin/python3 -I`), host idle.

## 1. Build

The 2.14.1 recipe carried over unchanged (`tools/release/build-torch-2.15.0.sh`): 1,362 s for torch (2.14.1: 1,414 s),
3,369 build steps, `-march=native` on 3,326 of 3,326 compile commands, the seeded AVX512 flags on the 12 fbgemm files
(`FindAVX.cmake` is unchanged, so the 2.14 trap still applies). New in the configure: `amd_smi` is a required package for
ROCm 7.14 and later (found in the ROCm 10.0 tree, 27.0.0; `libtorch_hip.so` links `libamd_smi.so`, which the
`amdrocm10.0-gfx906` dependency already brings). RCCL 2.30.4, hipFile 0.4.0, oneDNN 3.13.3, oneMKL 2026.2.1 static.

## 2. The typing_extensions gap

The first deb could not be imported by the system interpreter: `torch/jit/_check.py` and `torch/jit/_recursive.py` import
`Format` and `get_annotations` from `typing_extensions` (added in 4.13.0; the wheel declares `typing-extensions>=4.13.0`,
2.14.1 declared 4.10.0), and Ubuntu 24.04 ships 4.10.0. It was caught before the package was installed, by comparing the
wheel's requirements with noble and importing the staged tree with the system interpreter; the build venv, which has its
own 4.16.0, passed everything.

Fix: a second package in the same channel, **`python3-typing-extensions` 4.16.0-0exabit1** (Architecture all, 46 KB): the
unmodified upstream wheel (sha256 `481caa48...6370c2e8`, compared with PyPI's JSON API and with the module in the build
venv), under Ubuntu's package name, file layout and maintainer scripts, so apt upgrades noble's package in place. The
PyTorch deb depends on `python3-typing-extensions (>= 4.13.0)`. Why a backport and not a patch to the two files: PyTorch
raises this bound regularly (its build already asks for 4.15.0), and a patch has to find every new use by hand, where a
missed one fails only when that module is imported. The cost is that the channel upgrades a distribution package system-wide;
the 21 other modules tried on this box (rich, jsonschema, jwt, apt, requests, numpy, sympy and others) import with it.

Still declared and not satisfied on noble, as with 2.14.1: `sympy>=1.13.3` (1.12) and `setuptools>=77` (68). Nothing
tested needs them. **Corrected the same day:** the tests here did not exercise sympy; `torch.export` with dynamic shapes,
symbolic tracing and `torch.compile` fail with 1.12. Fixed by a `python3-sympy` 1.14.0 backport in the channel
(`2026-11-14-rocm-10.1.md` section 6).

## 3. Results, 2.14.1 against 2.15.0, same session

| | 2.14.1 | 2.15.0 |
|---|---|---|
| matmul 4096^3 per die, fp32 | 7.86-8.06 TF | 7.84-8.03 TF |
| fp16 / bf16 | 7.88-8.24 / 4.54-4.86 TF | 7.87-8.34 / 4.56-4.88 TF |
| RCCL all-reduce over 4 GPUs, 1 GiB (`stack_check.py`) | 48 ms, 20.95 GiB/s | 48 ms, 21.00 GiB/s |
| operator check (`torch-ops-check.py`) | 15 of 16 | 16 of 16 |
| `torch.distributed` `nccl` | legacy implementation, 21.10 GiB/s | rewritten implementation, 20.98 GiB/s |
| `nccl-lazy` / `nccl-legacy` | 20.95 / 21.08 GiB/s | 20.92 / 20.91 GiB/s |

n = 1 run per cell; the matmul ranges are over the four dies. Nothing moved beyond the box's 2% spread.

The operator check is new (`tools/release/torch-ops-check.py`): GPU against CPU, one check per ROCm library the package
links (rocBLAS, rocSOLVER, rocFFT, rocSPARSE, rocRAND, MIOpen), sort/topk/argmax, attention in fp32 and under autocast, a
two-layer transformer trained 30 steps (same loss on GPU and CPU, 0.1241), indexing, `cdist`, memory and serialization, and
the three NCCL backends over the four dies.

- **The one 2.14.1 failure is a real defect that 2.15.0 fixes:** `torch.topk` on the GPU with tied values returns the tied
  indices in a different order on two identical calls (rows of 5,000 elements; every k tried, 8 to 2,000). Values are
  right in both versions. 2.15.0 repeats the order (upstream #199425).
- **The rewritten NCCL backend, the default in 2.15, works on RCCL.** All-reduce, broadcast and all-gather are correct on
  all three backends. A group is bound to one device: pass `device_id` to `init_process_group`.

Package checks: apt refuses the PyTorch deb when the newer typing_extensions is not available (simulated install, rc 100);
all 51 ROCm libraries the binaries link belong to packages reachable from the `amdrocm10.0-gfx906` dependency. `ldd` on
the torchvision and torchaudio extension modules does not resolve `libtorch_cpu.so` / `libtorch_hip.so` by itself (they
have no RPATH to `torch/lib`, as in upstream's wheels); `import torch` loads them first, and the stack check exercises both.

## 4. Channel

Published with `tools/release/publish-torch.sh`: the per-version release `pytorch-2.15.0-gfx906-rocm10.0` (both debs, so
it resolves by itself) and the rolling channel `python3-torch-gfx906`: 2.13.0, 2.14.1, 2.15.0 and the typing_extensions
backport under one signed index. The two older debs are byte-identical to the assets of their own releases (the local
2.13.0 file was not; the channel copy was downloaded from the release and its digest checked).

On the box (`tools/release/dogfood-torch.sh`): source line switched to the channel, both packages reinstalled from it,
InRelease signature -> Packages SHA256 -> deb SHA256 -> origin signature verified for both, channel debs identical to the
local builds, stack check passes (21.20 GiB/s). Also exercised: rollback to 2.14.1 with noble's 4.10.0 through apt
(`--allow-downgrades`), where `apt-get upgrade -s` then lists both packages, and the upgrade back.

## 5. Open

- The ROCm apt repository also carries a 10.1 stream (`amdrocm10.1-gfx906`); this build stays on the installed 10.0.
- `nccl-legacy` and `TORCH_DIST_USE_NCCL2=0` disappear in the next PyTorch release; several GPUs in one process group
  need the legacy backend today.
- Anything on a machine that uses the system interpreter's torch (also a virtual environment created with
  `--system-site-packages`) is on 2.15.0 after the upgrade; 2.14.1 stays in the channel for going back.
