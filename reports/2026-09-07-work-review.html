Findings, most important first

  1. Host memory keeps logging correctable errorshardware
    Two more on memory controller 0, DIMM slot 2, this boot, on top of 13 on channel 0 on 3 September and a channel 1 event yesterday. No effect on GPU results, but a module that errors on every boot should be flagged before the machine is handed on.
  2. The MMVQ batch-16 patch existed only as uncommitted edits in a worktreefixed
    Three files, 88 insertions, in /root/llama.cpp-mmvq16 with nothing committed. The box is due to be wiped. Saved today as patches/mmvq-max-batch-16-b10288.patch in the benchmarking folder.
  3. The launch script did not offer the placement the guide adoptedfixed
    The README's busy-server answer since yesterday is two tensor-split pairs, one server per MPX module. settings/launch.sh claimed to wrap the winners but had no such profile and was not executable. A pairs profile is added and the mode bit set.
  4. The setup notes were three changes behindfixed
    They named kernel 7.0.0-30 and the W-3245, called the clamp unexplained, and listed only the smoke-test model. A dated amendments section now records the -31 kernel, the CPU swap, the SMC-envelope cause, the four builds and the serving model.
  5. The off-box copy is 60 MB of work inside 267 GB of rebuildable treesdecision
    Everything that cannot be regenerated totals 60 MB. The rest is three 37 GB kernel build trees, 142 GB of model files, a 24 GB logits file the Q4_1 job still needs, Geekbench and caches. An exclude list is in "For the product lead".
  6. The benchmarking folder is not versioned and its zip was staledecision
    Ten files were newer than the 02:57 snapshot. A tarball is now refreshed after each write-up (the box has no zip); a private repository is the right home, and where it goes is yours to say.
  7. Driver log noise: peer mapping refused by the chipsetbenign
    64 lines this boot of "PCIe P2P access from peer device is not supported by the chipset" and "Failed to map peer, mem_domain 2", in bursts of 4 to 16 at every multi-die process start. The kernel's PCI core does not whitelist this Xeon root complex for peer DMA, so another die's system-memory buffers cannot be mapped directly. Die-to-die VRAM traffic goes over XGMI and is unaffected: today's probes read 255.6 GB/s and the tensor-split numbers match 4 September within 2%. Not present in the saved logs of earlier boots because those predate ROCm on this box.
  8. One kernel warning per boot at process teardownbenign
    At 09:58:01, when the first XGMI probe exited: a pin-count underflow warning in the TTM buffer manager, reached from the KFD process-release worker. It is a warn-once, no functional effect was seen, and it plausibly follows from the refused peer mapping above. Tracked, not chased.
  9. The TODO's "minutes each" checks were never run; now donedone
    The HIP library carries only gfx906 code objects, 268 bundles and no generic fallback. HBM ECC is not exposed on these cards, so the ECC-cost test is moot. Transparent huge pages are on madvise. The IOMMU is on in translated mode; passthrough is not set and would need a reboot for a gain that is negligible for serving, where host-to-die traffic is small.
  10. Two capture defects in the faq scriptrerun done
    Its buffer-size fields came out empty and its two perplexity rows were dropped, both because the new build writes timestamped log lines the script's patterns did not expect. This build did not log the context sizes at all; the one hard number is the 9.5 GiB compute buffer in the out-of-memory line of the q8_0/q8_0 fit, and the perplexity rerun in the third queue captures the rest.
