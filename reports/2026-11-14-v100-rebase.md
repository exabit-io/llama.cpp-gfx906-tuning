## 2. MTP hidden rows: host, device, deferred

Upstream v1.0.0 lets the MTP draft context read the target's hidden rows from a device buffer (#31927). The fork defers the
first prompt's draft prefill and feeds it from a host buffer that the device mode does not fill, so the merge sequences
them: deferred prefill first, device rows once its buffer is released. Four arms on the merge build, `-np 1`, one long
prompt (2,089 tokens) then three identical short greedy requests (256 tokens each), n = 1 server per arm:

| Arm | Row path | Prefill, 2,089 tok | Decode, 3 x 256 tok | Drafts accepted |
|---|---|---|---|---|
| default | deferred prefill, then device rows | 548.6 tok/s | 71.7 / 70.7 / 70.9 tok/s | 154/200 |
| `LLAMA_MTP_DEV=0` | deferred prefill, host rows (the fork before v1.0.0) | 556.6 | 71.2 / 70.9 / 70.8 | 154/200 |
| `LLAMA_MTP_DEFERRED_PREFILL=0` | device rows from the start (upstream v1.0.0) | 539.0 | 71.2 / 70.5 / 70.8 | 154/200 |
| both off | host rows, per-chunk catch-up | 534.3 | 71.5 / 70.8 / 70.8 | 154/200 |

The greedy output is byte-identical in all four arms (same SHA-256 of the text, short and long request). With `-v` the two
device arms allocate the 40.02 MiB row buffer on the `Meta(ROCm0..3)` device and nothing falls back to the host; the host arms
allocate none. So upstream's device path works on the fork's tensor-parallel backend, and the choice is a matter of speed only:
decode is the same within the spread, and the deferred prefill is worth about 3% of prefill on this prompt (549-557 vs
534-539 tok/s, one sample per arm). With `-np 4` (no deferred prefill: more than one sequence) device rows and host rows are
again identical in output (156/197) and speed (75.5-76.0 vs 76.0-76.3 tok/s single stream).

The same four arms on master (RCCL on): prefill 750.5 / 750.9 / 715.1 / 711.4 tok/s, decode 74.4-74.7 / 73.6-74.0 /
73.5-73.7 / 73.4-73.9 tok/s, 154/201 accepted and identical output in all. The default is the fastest arm on both axes; the
deferred prefill is worth 5% of prefill there. v0.9.0 master's steady-state figure for the short request was 73.1 tok/s.

One request with `n_probs: 5` returns 5 `top_logprobs` on each of its 128 tokens. Four concurrent requests on `-np 4`
(device rows, four sequences) are coherent at 24.1-26.8 tok/s each (v0.9.0: 24.4-26.9), 63-76% of drafts accepted, no
refused rollback. All of these are smoke values at 8K context (R2.2), comparable build to build only.

## 3. Upstream bugs on HIP

Both are separate commits on the PR branch, CUDA unchanged.

- **Grouped top-k MoE ballot on 64-wide wavefronts** (the #23 fix, still needed): stock v1.0.0 fails 91 of 692 `TOPK_MOE`
  cases on a die, all with `n_expert_groups` > 1; the PR branch passes 692/692.
- **`PAD_REFLECT_1D` with 2^24 or more rows** (new): the kernel launches one 256-thread block per row along `grid.x`, and HIP
  rejects a launch with 2^32 or more threads along one grid dimension ("invalid configuration argument"). #31877 added a test
  case with 16,777,217 rows, so stock aborts there, 13,418 cases into `test-backend-ops`, and the remaining 6,970 cases never
  run. Measured with a minimal kernel on this box: accepted at 2^32 - 1 threads (2147483647 blocks of 2, 4294967295 blocks of
  1), rejected at 2^32 (16777216 blocks of 256, 2147483648 blocks of 2). The fix launches the rows in chunks on HIP; 7/7
  `PAD_REFLECT_1D` cases pass.

A fork-side defect that these merges did not introduce, found by upstream's `test-llama-context`: with all four dies visible,
`gemma4-dense` and `mistral-large4-moe` (2 of 144 dummy models) fail the sequence-copy cases `cp_h` / `cp_d`, gemma4 also
`frag`. Their KV-sharing layers land on different dies, which activates mxxm-t's KV replicas (de27e7509); a sequence copied
through a saved state then goes wrong at the second generated token. `LLAMA_KV_REPLICA=0` or one visible die passes all 144
models, stock v1.0.0 passes on four dies, and builds of the v0.9.0 and v0.7.0 merges fail the same way. `test-llama-archs`
writes the dummy models with new random weights on every run, and the count moves with them: gemma4-dense failed in all
three four-die runs (merge twice, master once), mistral-large4-moe in two of them (it passed the second merge run), so a run
reports 142 or 143 of 144. Reported to mxxm-t in #24. The 2026-11-06 report's "passes with one worker" cannot have had replicas in use (a build of that tree fails the same
cases on four dies today); how that run was restricted was not recorded. Upstream's new `test-fp8`
(requantize, FP8 KV cache on dummy models) and `test-llama-archs` (144 models) pass on the PR build.

**A disturbed A/B.** `np4-ab.sh` alternated source builds of the two masters at `-np 4` over three rounds (12:28-12:36 UTC).
From 12:30 on, 13 of the 27 requests on both builds lost 1-2 s (46-67 tok/s against 76-78): 3 of 9 on v0.9.0, 4 of 9 on
v1.0.0 with host rows, 6 of 9 on the v1.0.0 default. In the one server examined (v0.9.0, round 3) both slow requests ran their
first 242 tokens at full speed (79.8 and 80.1 tok/s) and lost the time in the last 14 tokens, one of them also in its prompt.
The graph-reallocation counts are the same in every server, fast or slow. A rerun on the installed package nine minutes later
(`stall-diag.sh`, verbose log) gave 8 of 8 requests at 76.6-77.2 tok/s; the largest gap between log lines inside a request was 279 ms in the first (saving the
long prompt's state) and 125-127 ms in the others (the context checkpoint). Not found:
the cause. Ruled out: a clock clamp (1730 MHz on all dies after the run), SMIs (count unchanged at 24), memory pressure (PSI
zero) and leaked VRAM (10 MiB per die idle). The A/B's means are therefore not usable; only the undisturbed requests are quoted.

## 7. Open

- PR #24 is open at mxxm-t (mergeable, no review yet). #23 is closed with a pointer.
- The fork's KV replicas and sequence state copy on four dies (section 3): reported in #24, not fixed here. It needs a model
  whose layers share KV rows; the Qwen models do not.
- The intermittent 1-2 s stalls of section 6: both builds, not reproduced nine minutes later, cause unknown. If they return,
  `stall-diag.sh` on a stalling server shows which log lines bracket the lost time.
- One physical page (pfn 0x5f3dd79, `CPU_SrcID#0_MC#1_Chan#2_DIMM#0`) logged a corrected memory error about once a minute
  whenever a llama process ran today; the kernel tried to soft-offline it 50 times and failed each time ("unhandlable page").
  This is the known DIMM problem, not a result of this cycle, and it was present in the undisturbed runs as well.
- Single-stream MTP at `-np 4`: about 2% below 0.9.0 (section 6), within the spread; not bisected.
- Not run: GGUFs from the v1.0.0 Qwen3.5 converter (merged `attn_qkv`/`ssm` tensors) against the GDN folds, an FP8 KV cache
  or FP8 weights on a real model, and anything at 64K depth: this cycle is a correctness pass at smoke depths, so the serving
  numbers of the guide still stand on the earlier builds.
- `python3-torch-gfx906` had only per-version releases; done later the same day with 2.15.0 (`2026-11-14-pytorch-2.15.0.md`).
