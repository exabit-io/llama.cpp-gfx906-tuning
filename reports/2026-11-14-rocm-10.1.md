# 2026-11-14: ROCm 10.1 - migration, a compiler regression in one kernel, both packages rebuilt, sympy backport

**What happened.** The box moved from the ROCm 10.0 stream to 10.1 (`10.1.0-gfx906+20261018172427`: HIP 7.16.26385,
LLVM 24, RCCL 2.30.7), installed beside 10.0. PyTorch 2.15.0 was rebuilt against it and published with a `python3-sympy`
backport that repairs `torch.export` and `torch.compile` on Ubuntu 24.04. mx-llama.cpp compiled by 10.1's toolchain is
correct but loses prefill speed (4.1 % at 1 x 255K); the loss is the code LLVM 24 generates for one kernel, and the ROCm
10.1 runtime does not touch prefill. The llama package for ROCm 10.1 is therefore compiled with ROCm 10.0's toolchain and
runs on 10.1's runtime; it passes the design-point acceptance with prefill equal to ROCm 10.0's and decode 0.7-1.0 %
lower, under the 2 % floor (section 5.1 says where that is). Record of the system changes: `tools/rocm101/README.md`
(`/root/rocm101-migration-20261114/README.md` on the box).

All runs: macpro2019-01, 4x gfx906, kernel 7.0.0-42 +barfix5, GPUs at 125 W by macpro-fand, mx-llama.cpp master `df2c6e5c5`,
Qwen3.8-27B Q8_0. The design-point cells are the survey's (`RE-RE-SURVEY-ACTION-PLAN.md` section 3): `llama-batched-bench`,
`-sm tensor`, f16/f16 KV, RCCL + gated custom AR, `-ntg 1024`; multi-user 4 x 64K, single-user 1 x 255K.

## 1. The stream

ROCm streams install side by side (`/opt/rocm/core-10.0`, `/opt/rocm/core-10.1`); `/opt/rocm/{lib,bin,...}` and the tools in
`/usr/bin` are alternatives that follow the newest stream. 64 new packages, none removed; the apt pin moved to
`10.1.0-gfx906*`. Library sonames are those of 10.0 (`libamdhip64.so.7`, `librocblas.so.5`, `librccl.so.1`, ...).

- **No `rocm-smi` in 10.1** (and no `librocm_smi64`); `amd-smi` replaces it (`amd-smi set -l HIGH`, `amd-smi set -o WATTS`).
  `tools/gpu-test-env.sh` now sets the DPM performance level through sysfs. macpro-fand never used either tool (it writes
  hwmon `power1_cap`), and `gfx906-rccl-topology` reads only sysfs.
- The 10.1 HIP link driver embeds `/opt/rocm/core-10.1/lib` as `DT_RPATH` in what it links; 10.0's did not.
- RCCL 2.30.7 reads `/etc/rccl.conf` and the generated topology as 2.30.4 did (PyTorch four-GPU all-reduce 21.1 GiB/s on both).

## 2. mx-llama.cpp compiled by and run on ROCm 10.1: correct

`test-backend-ops` 20388/20388 on each of the four dies; PPL 16K x 6 5.6093 +/- 0.0622; folds on 5.0822 (two runs), off
5.0575; `-sm layer -lm dio` 0 fallbacks; MTP 154/201; Flash-Next coherent; fixtures as on 10.0 (the fork's KV-replica
failure, 142 of 144). Every value and every output hash equals ROCm 10.0's. The compiler prints 13 "loop not unrolled"
warnings; they come from `softmax.cu` (12) and `ssm-scan.cu` (1), neither on this model's path.

## 3. Speed at the design points: the 10.1-compiled build is rejected

Rule written before any cell ran (`tools/rocm101/rocm-ab.sh`; the survey's `binstats.py` rule with a family of four tests):
n = 5 per arm per axis, arms alternated in seeded random order, multi-user mean / single-user median, two-sided exact
permutation, Benjamini-Hochberg q < 0.10, and an effect counts only at 2 % or more.

| Cell | Metric | ROCm 10.0 (compiled + runtime) | ROCm 10.1 (compiled + runtime) | Effect | p / q |
|---|---|---|---|---|---|
| 4 x 64K | decode, tok/s per slot | 24.672 (24.34-24.83) | 24.691 (24.65-24.71) | +0.08 % | 0.93 / 0.93 |
| 4 x 64K | prefill, tok/s | 806.1 (804.8-807.5) | 794.8 (793.4-796.1) | -1.39 % | 0.008 / 0.032 |
| 1 x 255K | decode, tok/s | 31.959 (31.89-31.97) | 31.961 (31.91-32.01) | +0.01 % | 0.71 / 0.93 |
| 1 x 255K | prefill, tok/s | 410.2 (409.9-410.2) | 393.3 (391.8-393.9) | **-4.13 %** | 0.048 / 0.095 |

Decode does not move under the rule. Prefill is lower in every 10.1 run on both axes; at 1 x 255K it crosses the
threshold, so the axis regresses and the build is rejected. (Read with section 5.1: two of the five ROCm 10.0 runs at
4 x 64K were low, 24.34 and 24.62 against 24.77-24.83 for the other three, and the mean hides a decode difference of about
half a percent that the later runs resolve.)

## 4. Where the loss is

**The compiler, not the runtime** (`rocm-cross.sh`, one run per arm per axis; the arms' spread in section 3 is 0.04-0.3 %):

| Arm | 1 x 255K prefill | 4 x 64K prefill |
|---|---|---|
| compiled by 10.0, run on 10.0 (section 3) | 410.2 | 806.1 |
| compiled by 10.0, **run on 10.1** | 410.8 | 805.1 |
| **compiled by 10.1**, run on 10.0 | 392.2 | 795.3 |
| compiled by 10.1, run on 10.1 (section 3) | 393.3 | 794.8 |

**One object file** (`swaplink.py` + `screen.sh`: the 10.1 build's library relinked with groups of objects taken from the
10.0 compiler; 1 x 128K, one run each):

| Library | 1 x 128K prefill, tok/s |
|---|---|
| ROCm 10.0 build | 602.2 |
| ROCm 10.1 build / the same relinked, nothing swapped | 586.7 / 589.2 |
| + only `fattn-tile-instance-dkq256-dv256.cu.o` from the 10.0 compiler | **604.3** |
| + all 99 flash-attention objects from 10.0 | 604.3 |
| + the 47 matrix-multiply objects from 10.0 | 588.0 |
| + the 4 gated-delta-net objects from 10.0 | 586.7 |
| + the other 65 objects from 10.0 | 587.6 |

The object holds the flash-attention tile kernels for head size 256; prefill of this model (GQA ratio 6) runs
`flash_attn_tile<256,256,16,2>`. Its cost grows with the KV length, which is why the loss grows with depth (1.4 % at 64K,
2.6 % at 128K, 4.1 % at 255K).

**What does not fix it.** Under our `max-ilp` scheduler LLVM 24 spills 16 vector registers in that kernel where LLVM 23
spilled 1 (the kernel sits at its 128-register cap, `amdgpu-waves-per-eu` = 2), which looked like the cause. It is not: a
variant with no spills at the same occupancy is no faster.

| Variant of the tile object, LLVM 24 | Spilled VGPRs (4x8 / 8x4 / 16x2) | 1 x 128K prefill |
|---|---|---|
| as built: `max-ilp`, table (256 threads, occupancy 2, nbatch_fa 32, nbatch_K 128) | 12 / 12 / 16 | 586.7-589.2 |
| `-amdgpu-sched-strategy=iterative-ilp` for the tile kernels | 0 / 0 / 0 | 579.7 |
| the compiler's default strategy for the tile kernels | 11 / 13 / 0 | 580.6 |
| table with nbatch_K 64 | 0 / 0 / 0 | 588.8 |
| table with occupancy 1 | 0 / 0 / 0 | 523.1 |
| the object from LLVM 23 (`max-ilp`) | 5 / 4 / 1 | 604.3 |

`max-ilp` is still the best strategy on LLVM 24; the difference to LLVM 23 is in the generated code itself and was not
pursued further. Across all 9,915 kernels of the library LLVM 24 spills more in 58 and fewer in 95; the FP8 (`f8_e4m3`)
flash-attention vec kernels for head 256 go from 0 to about 270 spilled registers, which matters to an FP8 KV cache (not
measured). Tools: `tools/rocm101/codegen/`.

### 5.2 Host compiler flags (screen)

The lead's question after 5.1: would another flag do better (`-march=x86-64-v4`, `-march=skylake-avx512`, `-mtune=intel`,
LTO, others)? `flag-builds.sh` builds the reference configuration once per flag set; only the host C/C++ flags change
(GPU code, `GGML_NATIVE=ON` and everything else as the reference). `flag-screen.sh` runs the installed package's
`llama-batched-bench` and GPU library with the six host libraries of one variant preloaded (ggml base, loader and CPU
backend, `libllama`, `libllama-common`, the bench library), on the ROCm 10.1 runtime, at 4 x 64K.

| Arm | Host flags | 256-bit / 512-bit instructions in `libllama` |
|---|---|---|
| base | none (the reference build) | 0 / 0 |
| native | `-march=native` (the deb; gcc 13.3 resolves it to cascadelake, which prefers 256-bit vectors) | 5,018 / 0 |
| skx | `-march=skylake-avx512` | 5,018 / 0 |
| v4 | `-march=x86-64-v4` (generic tuning: 512-bit vectors) | 2,076 / 3,830 |
| tintel | `-march=native -mtune=intel` (512-bit vectors) | 3,073 / 3,740 |
| novec | `-march=native -fno-tree-vectorize` (diagnostic: the instruction set without auto-vectorized loops) | 1,136 / 0 |
| o2 | `-O2` instead of CMake's `-O3` | 0 / 0 |
| nosemi | `-fno-semantic-interposition`, libraries linked `-Bsymbolic-functions` (calls inside `libllama` stop going through the PLT: 2,424 -> 522 PLT relocations) | 0 / 0 |
| lto | `-flto=auto` | 0 / 0 |
| ltonosemi | both | 0 / 0 |
| pgo | ltonosemi + profile-guided, trained on one run of this same cell (a ceiling, not a recipe) | 0 / 0 |

With `GGML_NATIVE=ON`, ggml's CPU backend is compiled for the native CPU in every arm (its own flag comes after the
global one), so none of these changes its SIMD kernels; in this cell every layer is on the GPUs anyway.

Reading, written in the script before the first cell: a screen, n = 3 blocks, every arm once per block in a seeded random
order, statistic the mean decode per slot. An arm matches a control (base or native, 0.10 tok/s apart in 5.1 with ranges
0.04 wide) when its range overlaps that control's and not the other's; it is better than base only if every run is above
every base run. Anything that would change the package is confirmed on a built package with the acceptance rule.

Results (2026-11-15, 02:52-06:19 UTC; 33 cells, none discarded). Decode in tok/s per slot, mean of n = 3 with the range;
prefill is 805.6-807.7 tok/s in every cell.

| Arm | Decode | Step | Against base | The three runs | By the rule |
|---|---|---|---|---|---|
| base | 24.672 (24.653-24.700) | 40.53 ms | | 24.662, 24.653, 24.700 | control |
| nosemi | 24.664 (24.639-24.687) | 40.55 ms | -0.03 % | 24.639, 24.666, 24.687 | matches base |
| novec | 24.660 (24.652-24.665) | 40.55 ms | -0.05 % | 24.665, 24.652, 24.665 | matches base |
| lto | 24.626 (24.604-24.661) | 40.61 ms | -0.19 % | 24.604, 24.612, 24.661 | overlaps both controls: not resolved |
| ltonosemi | 24.592 (24.565-24.616) | 40.66 ms | -0.32 % | 24.616, 24.565, 24.596 | matches native |
| skx | 24.582 (24.558-24.620) | 40.68 ms | -0.36 % | 24.569, 24.558, 24.620 | matches native |
| pgo | 24.574 (24.552-24.588) | 40.69 ms | -0.40 % | 24.588, 24.552, 24.581 | matches native |
| native | 24.571 (24.528-24.605) | 40.70 ms | -0.41 % | 24.605, 24.581, 24.528 | control |
| v4 | 24.520 (24.505-24.548) | 40.78 ms | -0.62 % | 24.506, 24.505, 24.548 | matches native (two of three runs are below every native run) |
| tintel | 24.482 (24.467-24.499) | 40.85 ms | -0.77 % | 24.467, 24.479, 24.499 | below both controls |
| o2 | 24.353 (24.341-24.362) | 41.06 ms | -1.29 % | 24.362, 24.355, 24.341 | below both controls |

- **No arm is better than base.** The controls reproduce 5.1: 0.101 tok/s apart (24.657 and 24.558 there), ranges
  disjoint, though wider in this session (0.047 and 0.077).
- **The cost of `-march=native` is in auto-vectorized loops, not in the instruction set.** The native instruction set with
  the vectorizer off (novec) equals base; `-march=skylake-avx512` equals native (the same 256-bit code); the two arms
  that vectorize at 512 bits are lower again (-0.62 % and -0.77 %). Which loops, and why vector code is slower there, was
  not measured.
- **Link-time and profile-guided optimization do not help.** LTO is between the controls, LTO with
  `-fno-semantic-interposition` 0.3 % under base, and the profile-guided build on top of that, trained on this very cell,
  is no better (24.574). `-fno-semantic-interposition` with `-Bsymbolic-functions` alone equals base: the PLT calls
  inside `libllama` cost nothing measurable.
- **`-O2` is the largest effect in the screen, and a loss: -1.29 %** (+0.53 ms per step). CMake's Release `-O3` on the
  host code is worth that much decode at 4 x 64K. It also shows how much of the 40.5 ms step is host code that a
  compiler setting can move.

**Selected: the reference configuration's flags** (CMake Release defaults, `-march=native` only where `GGML_NATIVE` puts
it). For the deb that means dropping `-DCMAKE_C_FLAGS`/`-DCMAKE_CXX_FLAGS=-march=native` from
`build-mx-llama-deb.sh`, expected gain 0.4 % of 4 x 64K decode. This is a screen at one cell: the change goes into the
next package build and is confirmed there with the acceptance rule at both design points, including 1 x 255K, which no
flag arm ran.

Version scheme: the 10.0 and 10.1 streams carry the same build stamp, so the stream is in the version,
`<upstream>+git<date>.<sha>.rocm<stream>.gfx906.<stamp>` (PyTorch: `<upstream>+rocm<stream>.gfx906.<stamp>`); both sort
above the 10.0 builds for apt and for pip.

A machine on ROCm 10.0 that upgrades gets the 10.1 runtime added by apt, nothing removed: 15 packages, 284 MiB to
download, 1.6 GiB installed for this package; 29 packages, 717 MiB, 3.5 GiB for PyTorch's `amdrocm10.1-gfx906`.
The ROCm 10.0 builds of the llama package have no ROCm path of their own: once 10.1 is installed they run on it (that is
the configuration `suite-mixed.sh` tested).

## 6. PyTorch 2.15.0 on ROCm 10.1, and its Python dependencies

`python3-torch-gfx906` `2.15.0+rocm10.1.gfx906.20261018172427-1`, same source and recipe as the morning's ROCm 10.0 build.

| | ROCm 10.0 build | ROCm 10.1 build |
|---|---|---|
| matmul 4096^3 per die, fp32 / fp16 / bf16, TF | 7.84-8.07 / 7.92-8.30 / 4.55-4.84 | 7.84-8.03 / 7.91-8.28 / 4.56-4.86 |
| RCCL all-reduce over 4 GPUs, 1 GiB | 21.10 GiB/s | 21.13 GiB/s |
| operator check (`torch-ops-check.py`) | 16 of 16 | 16 of 16 |
| `torch.distributed` `nccl` / `nccl-lazy` / `nccl-legacy`, GiB/s | 21.09 / 20.93 / 21.07 | 21.36 / 21.30 / 21.12 |

**sympy.** PyTorch 2.15 declares `sympy>=1.13.3`; Ubuntu 24.04 has 1.12. The morning's report called the gap harmless.
It is not: `tools/release/torch-pydeps-check.py` (CPU only) shows `torch.export` with dynamic shapes, symbolic tracing
and `torch.compile(dynamic=True)` failing with `ImportError: cannot import name '_args_sortkey' from 'sympy.core.basic'`.
The channel now carries `python3-sympy` 1.14.0-2~24.04.exabit1 with `isympy-common` and `isympy3`: Ubuntu 26.04's source
package rebuilt for 24.04 in a clean noble chroot (`tools/backports/build-backport.sh`; source fetched with `apt-get source`
and verified against the Ubuntu archive key; the only change is the changelog entry; built with `nocheck nodoc`). With it
all three work, and the PyTorch deb depends on `python3-sympy (>= 1.13.3)`.

**ninja.** `torch.utils.cpp_extension.load` stops with "Ninja is required to load C++ extensions" on a machine without
it; the deb now recommends `ninja-build` and `g++`. With both, 6 of 6 checks pass.

**setuptools: not replaced.** PyTorch declares `setuptools>=77.0.3`; Ubuntu 24.04 has 68.1.2. The bound is PyTorch's own
build metadata requirement (setuptools 77 is the first with PEP 639 licence fields); at run time it imports setuptools
only for `torch.utils.cpp_extension`, and building a C++ extension through setuptools 68 passes. Satisfying the bound
means replacing `python3-setuptools`, `python3-pkg-resources` and `python3-wheel` (78.1.1 breaks wheel < 0.46) on every
node, and Ubuntu 26.04's setuptools uses eight de-vendored libraries (jaraco.*, more-itertools, typeguard, zipp, inflect,
autocommand) whose 24.04 versions are far older. On this box `ubuntu-pro-client` and 19 other installed packages depend on
`python3-pkg-resources`, and pip on setuptools and wheel. Left as a declared-but-unsatisfied requirement that `pip check` reports; the lead's decision if wanted.

## 7. Open

- The head-256 tile kernel under LLVM 24: why the generated code is slower is not known. Until a compiler passes the
  design-point A/B, the llama package needs ROCm 10.0's toolchain on the build host (`COMPILERSTREAM=10.0`).
- ROCm 10.0 stays installed on the build host for that reason; nodes need only the 10.1 runtime.
- Not measured on ROCm 10.1: the candidates branch, FP8 KV caches (see the spill note in section 4), anything through
  PyTorch beyond the checks above.
- The deb's host flag: `-march=native` on the host code outside ggml costs 0.4 % of 4 x 64K decode (section 5.1), in
  every deb so far. None of ten alternatives beats building without it (section 5.2). The published package still
  carries the flag: the next package build drops it and is confirmed with the acceptance rule; no rebuild for 0.4 %
  alone. Not determined: which vectorized loops cost the time, and whether 1 x 255K behaves the same.
- Host code is worth more than assumed: `-O2` against `-O3` on the host libraries moves 4 x 64K decode by 1.3 %
  (section 5.2). Host-side options beyond the eleven arms (clang as the host compiler, `-O3` with selected loops
  unvectorized) were not tried.
- The ROCm 10.1 runtime's 0.6 % of decode at 4 x 64K (same binaries, HIP 7.16 against 7.15): not investigated.
- GPU-side compile options other than the scheduler strategy (inlining, unrolling) have not been surveyed. LLVM 24 moved
  prefill 4 % through one kernel, so that is where compiler options have leverage.
- `setuptools` (section 6): the lead's decision.
