# 2026-11-14: ROCm 10.1 - migration, a compiler regression in one kernel, both packages rebuilt, sympy backport

**What happened.** The box moved from the ROCm 10.0 stream to 10.1 (`10.1.0-gfx906+20261018172427`: HIP 7.16.26385,
LLVM 24, RCCL 2.30.7), installed beside 10.0. PyTorch 2.15.0 was rebuilt against it and published with a `python3-sympy`
backport that repairs `torch.export` and `torch.compile` on Ubuntu 24.04. mx-llama.cpp compiled by 10.1's toolchain is
correct but loses prefill speed (4.1 % at 1 x 255K); the loss is the code LLVM 24 generates for one kernel, and the ROCm
10.1 runtime does not touch prefill. The first llama package for ROCm 10.1 (2026-11-14) was therefore compiled with
ROCm 10.0's toolchain and ran on 10.1's runtime, with prefill equal to ROCm 10.0's and decode 0.7-1.0 % lower.

**2026-11-15.** The decode difference was split into the package's global `-march=native` (0.4 %, section 5.1; ten
alternatives screened, none better than no flag, section 5.2) and the 10.1 runtime (0.3 %: ROCr's event thread now
sleeps between polls, section 5.3). The kernel loss was traced to LLVM 24's code generator and removed with one
scheduler option on one object (section 4.1). A survey of sixteen GPU-side compile options found nothing faster than
the shipped flags (section 5.4). The package was rebuilt as `-r1`: master `290fc642a` (the one CMake rule), compiled
by ROCm 10.1's toolchain, no global host flag. Against the ROCm 10.0 source build it reads prefill +0.27 % and +0.28 %,
decode -0.52 % at 4 x 64K and +0.05 % at 1 x 255K, all under the 2 % floor (section 5.6). Record of the system
changes: `tools/rocm101/README.md` (`/root/rocm101-migration-20261114/README.md` on the box).

All runs: macpro2019-01, 4x gfx906, kernel 7.0.0-42 +barfix5, GPUs at 125 W by macpro-fand, mx-llama.cpp master `df2c6e5c5`,
Qwen3.8-27B Q8_0. The design-point cells are the survey's (`RE-RE-SURVEY-ACTION-PLAN.md` section 3): `llama-batched-bench`,
`-sm tensor`, f16/f16 KV, RCCL + gated custom AR, `-ntg 1024`; multi-user 4 x 64K, single-user 1 x 255K.

### 4.1 The cause (2026-11-15)

All arms below are the 10.1 build on the 10.1 runtime with only the tile object replaced, 1 x 128K prefill, n = 2 per
arm, reading rules written in the scripts before the first cell (`drv-test.sh`, `tile2-screen.sh`). The machine state
differs from the tables above (section 5.3), so the controls are repeated in every screen.

**Not the driver's pipeline.** clang 24's HIP driver defaults to the new offload driver, which emits device code as
bitcode and compiles it at link time through the full-LTO pipeline (`cc1 -emit-llvm-bc -flto=full`, then
`clang-linker-wrapper`); clang 23 compiled it directly (`cc1 -emit-obj`). Both compilers can do both:

| Tile object compiled by | Device pipeline | Spilled VGPRs (4x8 / 8x4 / 16x2) | 1 x 128K prefill, tok/s |
|---|---|---|---|
| clang 23 (as the reference build) | direct | 5 / 4 / 1 | 605.7 (605.7-605.8) |
| clang 23 `--offload-new-driver -foffload-lto=full` | full LTO | 5 / 4 / 1 | 605.3 (605.2-605.4) |
| clang 24 (as the 10.1 build) | full LTO | 12 / 12 / 16 | 590.3 (590.2-590.3) |
| clang 24 `--no-offload-new-driver` | direct | 12 / 12 / 16 | 590.7 (590.3-591.0) |
| clang 24 `-fno-offload-lto` | direct, new driver | 12 / 12 / 16 | 590.7 (590.6-590.8) |
| clang 24 `-foffload-lto=thin` | thin LTO | 11 / 16 / 0 | 583.0 (582.9-583.1) |

The speed follows the compiler, not the pipeline (2.5 %, 15 tok/s, against a block-to-block spread of 0.1-0.7).

**The code generator, not the optimizer** (`tile2-build.sh`, `tile2-screen.sh`). Each compiler's optimized device bitcode
was run through the other compiler's code generator (`codegen/ircross.py`; the method reproduces clang 23's object byte for
byte and clang 24's hot loop when optimizer and code generator are the same compiler). Decode is the same cell's 256
generated tokens (one stream at 128K depth), which run the object's `flash_attn_tile<256,256,1,2>` kernel.

| Tile object | Spilled VGPRs (4x8 / 8x4 / 16x2) | 16x2 hot loop: instructions / spill reloads / waits | prefill, tok/s | decode, tok/s |
|---|---|---|---|---|
| clang 23 (control) | 5 / 4 / 1 | 1883 / 0 / 9 | 605.3 (604.5-606.1) | 40.20 (40.14-40.25) |
| clang 24 (control) | 12 / 12 / 16 | 1906 / 10 / 13 | 589.3 (589.0-589.7) | 40.18 (40.18-40.19) |
| clang 23's optimized bitcode, clang 24's code generator | 10 / 14 / 18 | 1910 / 11 / 14 | 590.9 (590.5-591.3) | 40.14 (40.06-40.21) |
| clang 24's optimized bitcode, clang 23's code generator | 5 / 4 / 1 | 1880 / 0 / 9 | 606.0 (605.7-606.3) | 40.24 (40.21-40.26) |
| clang 23, the compiler's default scheduler instead of `max-ilp` | 0 / 0 / 1 | 1883 / 0 / 9 | 603.8 (603.8-603.8) | 40.04 (40.04-40.05) |
| clang 24 `-mllvm -amdgpu-vgpr-threshold-percent=90` | 2 / 1 / 0 | 1894 / 0 / 9 | 606.4 (606.1-606.7) | 40.06 (40.04-40.08) |
| clang 24 `-mllvm -amdgpu-use-amdgpu-trackers=1` | 0 / 0 / 0 | 1889 / 0 / 9 | 604.0 (604.0-604.0) | **38.17** (38.14-38.20) |
| clang 23 `-mllvm -amdgpu-use-amdgpu-trackers=1` | 1 / 4 / 1 | 1880 / 0 / 9 | 603.8 (603.7-603.9) | **38.18** (38.12-38.23) |

By the written rule (controls apart by more than 8 tok/s in each block: 16.4 and 15.4; "fast" = every sample within 4
tok/s of clang 23's mean, "slow" = within 4 of clang 24's): clang 23's bitcode through clang 24's code generator is slow
and the reverse is fast, so **the loss is made in LLVM 24's code generator**. The optimizer's output is interchangeable.

What the code generator does differently: under `max-ilp` more vector registers are live across the 16x2 kernel's
inner loop than the 128 the kernel may use, and the register allocator then reloads 10 spilled registers from the stack
in every iteration (4 more waits on memory). (This section took the scheduler for the origin; section 4.2 finds it one
pass earlier.) Ten single scheduler and allocator switches tried
on clang 24 leave the spills as they are (static comparison only: `amdgpu-schedule-relaxed-occupancy=1`,
`amdgpu-disable-unclustered-high-rp-reschedule`, `amdgpu-disable-clustered-low-occupancy-reschedule`,
`amdgpu-enable-rewrite-partial-reg-uses=0`, `amdgpu-schedule-metric-bias` 0 and 100,
`amdgpu-scheduler-pending-queue-limit=0`, `amdgpu-opt-vgpr-liverange=0`, `amdgpu-enable-pre-ra-optimizations=0`,
`amdgpu-dce-in-ra=0`). Two others remove them:

- `-amdgpu-vgpr-threshold-percent=N` (new in LLVM 24: scales the VGPR limit the scheduler works to): 95 leaves 9 spills in
  the 16x2 kernel, 90 none (123 registers used), 85 to 50 none with fewer registers. At 90 prefill is back at clang 23's
  level. The switch changes 21 of the object's 77 kernels. The decode kernel is not one of them: `<256,256,1,2>` is
  byte-identical to clang 24's, so the decode column's 40.06 is the control's figure (the eight non-tracker rows span
  40.04-40.26). Decode with several slots runs the same kernel (each sequence is its own stream, one query column
  each: `llama-graph.cpp`, `fattn-tile.cuh`).
- `-amdgpu-use-amdgpu-trackers=1` (off by default in both compilers): no spills in any of the three kernels, and with it
  the two compilers schedule the hot loop nearly alike (instruction-order similarity 0.957, against 0.775 with the default
  trackers), which seemed to place the divergence in LLVM 24's generic register-pressure tracking as the GCN scheduler
  uses it. (Wrong: the bisect of section 4.2 puts it in machine LICM, which runs before the scheduler and hands it a
  loop with more live values.) **The switch is not usable:** on both compilers it reschedules the decode kernel
  (`<256,256,1,2>`: 841 / 829 instructions and 89 / 86 waits in the hot loop against 856-864 and 118) and decode at 128K
  depth drops 5.0 % (2.0 tok/s, four samples of four, against a spread of 0.2 among the other twelve).

Standing of the fix: in this table threshold 90 on the one object is measured at one design point with n = 2. Section
5.5 takes it through two cells against the ROCm 10.0 compiler, and section 5.6 through the design-point acceptance as a
package.

### 4.2 The LLVM commit, and the fix ROCm 10.1 does not have (2026-11-16)

Bisected. Section 4.1's reading of the mechanism is corrected here: the scheduler is where a switch helps, but the
change is in machine LICM, one pass earlier.

**Method** (`tools/rocm101/llvm-bisect/`). The two compilers name their commits in ROCm/llvm-project: ROCm 10.0's
clang 23 is `8f497e0992fb`, ROCm 10.1's clang 24 is `d6f6cb691863`; their merge base is `7f7028776eb2` (2026-06-04),
10,434 commits before 10.1's. Because the loss is made in the code generator (section 4.1), each step builds only `llc`
(AMDGPU target) at the commit under test, compiles clang 23's optimized bitcode of the tile translation unit as the tree
does (`-O3 -mcpu=gfx906 -amdgpu-sched-strategy=max-ilp`), and counts the scratch reloads in the 16x2 kernel's inner loop
(`codegen/loopstat.py`): good at 0 or 1, bad at 5 or more. The endpoints read as the compilers do: `llc` at ROCm 10.0's
commit and at the merge base 1883 instructions / 0 reloads / 9 waits (its object is byte-identical to clang 23's in
`.text`), at ROCm 10.1's commit 1910 / 11 / 14 (section 4.1's row for clang 23's bitcode through clang 24's code
generator). 13 steps, none skipped, every step 0 or 11.

**First bad commit: `80df471b75d0`, "Reland [MachineLICM] Use `RegisterClassInfo::getRegPressureSetLimit` (#213584)"**
(upstream LLVM, 2026-08-03). It changes one line of behaviour: machine LICM takes the register-pressure limit it hoists
against from `RegisterClassInfo` (the target's limit minus an estimate for reserved registers) instead of from the
target. On AMDGPU that subtraction is unsigned and wraps. Printed from `llc` at ROCm 10.1's commit for the 16x2 kernel:
`VGPR_32` target limit 128, limit machine LICM receives **4,294,965,632**; `SReg_32` 102 and 52; `AGPR_32` 128 and 128.
The limits differ in all 75 functions of the translation unit. With no vector-register limit, machine LICM hoists
everything it can out of the loop, more values stay live across it than the kernel's 128 registers hold, and the
allocator spills (18 VGPRs in the 16x2 kernel against 1).

**Upstream fixed it sixteen days later, and ROCm 10.1 was cut in between.** `1d7d16b94c61`, "[CodeGen] Avoid register
pressure limit underflow (#216372)" (2026-08-19; its message names machine LICM and MachineSink as the passes that
exposed the underflow). The last upstream commit in ROCm 10.1's compiler is `fc636be1b4c2` of
2026-08-13. `d6f6cb691863` is the tip of ROCm/llvm-project's `release/therock-10.1`; that branch and
`gpuep-releases/therock-10.1` (tip of 2026-11-10) contain the first commit and not the fix. `amd-staging` has the fix
since its merge of 2026-08-19, and the `therock-10.2` and `therock-10.3` branches have it (all still LLVM 24).

What follows from it:

- **The bug is in one release of the compiler.** ROCm 10.0's predates the change and ROCm 10.2's branches have the
  fix. The tree's rule was found as a workaround for it; section 4.3 shows that it is worth keeping on a compiler
  without the bug as well, so it stays keyed on "clang 24 or newer".
- **The bug is not specific to this kernel.** Every kernel ROCm 10.1 compiles gets machine LICM (and MachineSink)
  without a vector-register limit. Here it costs time in the one kernel that runs out of registers under `max-ilp`;
  the acceptance (section 5.6) shows no other loss at the two design points, and nothing else was looked at.
- **Nothing to report to LLVM.** A report to ROCm would ask for `1d7d16b94c61` on the 10.1 release branches; a draft
  with a single-function reproducer (`tools/rocm101/llvm-bisect/repro/tile-16x2.ll.gz`: ROCm 10.0's `clang -cc1` gives 0
  reloads on it, ROCm 10.1's 11) is in `tools/rocm101/llvm-bisect/ISSUE-DRAFT.md`. Not filed: the lead's decision.

### 4.3 The rule on a compiler that has the fix (2026-11-16)

`llvm-bisect/fixrule-screen.sh`: section 4.2's method and cell (1 x 128K prefill, only the tile object replaced), n = 3,
arm order shuffled in each block. Rule written before the first cell: the question is read only if the fixed compiler
without the rule is again below clang 23 in every sample, and the rule "adds" if every sample with it is above every
sample without it. All `llc` rows are built at ROCm 10.1's compiler commit.

| Tile object | 16x2 hot loop: instructions / reloads / waits | Spilled VGPRs (4x8 / 8x4 / 16x2) | Prefill, tok/s |
|---|---|---|---|
| clang 23 (control) | 1883 / 0 / 9 | 5 / 4 / 1 | 604.5 (604.3-604.5) |
| `llc` + the fix | 1883 / 0 / 9 | 5 / 4 / 1 | 600.9 (600.8-601.0) |
| `llc` + the fix, `-amdgpu-vgpr-threshold-percent=90` | 1888 / 0 / 9 | 0 / 0 / 0 | **606.9** (606.8-607.1) |
| `llc` without the fix, `-amdgpu-vgpr-threshold-percent=90` (what the tree builds today) | 1897 / 0 / 9 | 2 / 1 / 0 | 605.4 (605.1-605.6) |

- The fixed compiler without the rule is 3.6 tok/s (0.59 %) under clang 23 in every sample, as in section 4.2.
- **The rule adds 6.0 tok/s (1.0 %) on the fixed compiler**, every sample above every sample without it: 0.40 % above
  clang 23's object and 0.25 % above today's. Threshold 90 is therefore not only a workaround for the bug; it is the
  better setting for this object under LLVM 24. **The rule stays when ROCm's compiler has the fix** (with the two-cell
  check of section 5.5 on that compiler, as for any compiler change).
- With the fix, threshold 90 changes 19 of the object's 75 functions; the decode kernel `<256,256,1,2>` is not one of
  them. Decode in the same cells (256 tokens at 128K depth) is listed, not read: clang 23 40.18-40.25 tok/s, fix
  40.08-40.12, fix with the rule 40.11-40.19, today's 40.12-40.26.
- One object, one cell, n = 3. The option does not exist in LLVM 23, so there is no clang 23 row with it.

`perf stat` attached to the bench process for its 330 s (`PERF=1 TAG=rt-perf`; diagnostic, n = 1, not a timing result:
decode 24.812 with ROCr from 10.0, 24.773 all-10.1, step 40.30 against 40.37 ms):

| Bench process over 330 s | ROCr from 10.0 | all 10.1 |
|---|---|---|
| CPU time (task-clock) | 893.8 s | 577.5 s |
| context switches | 96,003 | 1,380,026 |
| `ioctl` / `futex` / `poll` calls | 48,316 / 174,814 / 5,585 | 50,986 / 174,833 / 5,593 |
| cycles in `rocr::core::Runtime::AsyncEventsLoop` | 35.9 % (about 321 CPU-s) | 0.22 % (about 1.3 CPU-s) |
| cycles in `rocr::core::BusyWaitSignal::WaitRelaxed` | 57.4 % (about 513 CPU-s) | 89.2 % (about 515 CPU-s) |

ROCr's async-events thread watches the signals that have completion handlers; those without a kernel event it has to
poll. The 10.0 library polls them in a loop without sleeping, which keeps one host core busy for the whole run; in the
10.1 library the same function calls `rocr::os::uSleep` between scans and doubles the nap up to a ceiling (disassembly
of both; the 10.0 function has no such call). The public ROCr source documents the change: the loop "monopolizes a CPU
core" without a sleep, so it naps between scans, in the current source from 20 us doubling to 200 us while interrupts
are available (the shipped binary's two constants were not read). A polled signal is therefore seen up to one nap
late, which fits the 0.06-0.13 ms per 40.3 ms step. Everything else in the profile is the
same (the dispatch-side busy wait is 513 against 515 CPU-s; the three counted system calls agree within 6 %).

So the 10.1 runtime's decode cost is not a defect: it gives up 0.3 % of decode for a whole host core (316 CPU-s less
per 330 s). The nap bounds are compile-time constants in the public source and neither library has an environment
switch for them. Not determined: which signals are the polled ones here (the source names IPC signals, plain signals,
and interrupt signals created after the kernel events ran out), and so whether the polling could be avoided altogether.

**sympy.** PyTorch 2.15 declares `sympy>=1.13.3`; Ubuntu 24.04 has 1.12. The morning's report called the gap harmless.
It is not: `tools/release/torch-pydeps-check.py` (CPU only) shows `torch.export` with dynamic shapes, symbolic tracing
and `torch.compile(dynamic=True)` failing with `ImportError: cannot import name '_args_sortkey' from 'sympy.core.basic'`.
The channel now carries `python3-sympy` 1.14.0-2~24.04.exabit1 with `isympy-common` and `isympy3`: Ubuntu 26.04's source
package rebuilt for 24.04 in a clean noble chroot (`tools/backports/build-backport.sh`; source fetched with `apt-get source`
and verified against the Ubuntu archive key; the only change is the changelog entry; built with `nocheck nodoc`). With it
all three work, and the PyTorch deb depends on `python3-sympy (>= 1.13.3)`.

**ninja.** `torch.utils.cpp_extension.load` stops with "Ninja is required to load C++ extensions" on a machine without
it; the deb now recommends `ninja-build` and `g++`. With both, 6 of 6 checks pass.

**setuptools: not replaced.** PyTorch declares `setuptools>=77.0.3`; Ubuntu 24.04 has 68.1.2. The bound is PyTorch's own
build metadata requirement (setuptools 77 is the first with PEP 639 licence fields); at run time it imports setuptools
only for `torch.utils.cpp_extension`, and building a C++ extension through setuptools 68 passes. Satisfying the bound
means replacing `python3-setuptools`, `python3-pkg-resources` and `python3-wheel` (78.1.1 breaks wheel < 0.46) on every
node, and Ubuntu 26.04's setuptools uses eight de-vendored libraries (jaraco.*, more-itertools, typeguard, zipp, inflect,
autocommand) whose 24.04 versions are far older. On this box `ubuntu-pro-client` and 19 other installed packages depend on
`python3-pkg-resources`, and pip on setuptools and wheel. Left as a declared-but-unsatisfied requirement that `pip check` reports; the lead's decision if wanted.

## 7. Open

- The head-256 tile kernel under ROCm 10.1's compiler: bisected to LLVM `80df471b75d0` (machine LICM's pressure limit
  wraps on AMDGPU), fixed upstream by `1d7d16b94c61`, which ROCm 10.1's release branch does not have and ROCm 10.2's
  does (section 4.2). The fork compiles that one object with `-amdgpu-vgpr-threshold-percent=90` when the HIP compiler
  is LLVM 24 or newer (`290fc642a`), which removes the loss at both design points (sections 5.5, 5.6) and is worth
  keeping on a compiler with the fix (section 4.3). Open: the report to ROCm (asking for the fix on the 10.1 release
  branches) is drafted with a reproducer and not filed, the lead's decision. A later compiler, or a change to the tile
  kernel, needs the two-cell check of section 5.5 again. Whether the same bug costs anything in kernels outside the two
  design points (other head sizes, other quantizations, the FP8 caches) was not looked at.
- ROCm 10.0 is no longer needed to build the llama package. It is still installed on this box (the reference builds of
  this report run on it); removing it is the lead's decision.
- The package's decode at 4 x 64K is 0.5 to 0.6 % under the ROCm 10.0 source build (sections 5.6, 5.7). All of it is
  the ROCm 10.1 runtime (section 5.3: its async-events thread naps between polls where 10.0's spun a host core; not a
  defect, no environment switch, nothing to ship); the package's own code has no share that n = 5 separates (section
  5.7: -0.08 %). Closed.
- Host flags: the package is built without the global `-march=native` since `-r1` (sections 5.1, 5.2, 5.6). Which
  vectorized loops cost the time under the flag was not determined. Host code is worth more than assumed: `-O2`
  against `-O3` on the host libraries moves 4 x 64K decode by 1.3 % (section 5.2); host-side options beyond the eleven
  arms (clang as the host compiler, `-O3` with selected loops unvectorized) were not tried.
- GPU-side compile options: surveyed (section 5.4), sixteen variants timed at 4 x 64K, none faster than the shipped
  flags, several far slower. Each was one sample at one cell with the ROCm 10.0 compiler; the survey was not repeated
  with LLVM 24 or at 1 x 255K. `iterative-ilp` on every source could not be built (the ROCm 10.0 compiler crashes in
  its register allocator on two sources; not reported upstream).
- The ROCm 10.0-stream packages in the channel were not rebuilt: they still carry the global `-march=native`.
- Not measured on ROCm 10.1: the candidates branch, FP8 KV caches (see the spill note in section 4), anything through
  PyTorch beyond the checks above.
- `setuptools` (section 6): the lead's decision.
